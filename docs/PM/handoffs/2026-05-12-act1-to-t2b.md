### 2.2 작업 분해

#### T2B-1.1 — 시드 가능 PRNG 인프라 (~0.5일)

**현황**: `web/js/game/dungeon-generator.js` 가 이미 mulberry32 PRNG + seed 인자를 갖고 있음. 그러나 *generator 안에 갇혀 있어* 다른 모듈에서 재사용 불가.

**작업**:
1. `web/js/game/rng.js` 신규 모듈 작성:
   - `mulberry32(seed: uint32): () => float [0,1)` — 기존 generator 의 함수와 동일 구현
   - `hashStringSeed(str: string): uint32` — `'2026-05-12'` 같은 문자열 → 32-bit seed. 단순 FNV-1a 또는 cyrb53 후 mask 32-bit
   - `dailySeed(date: Date = new Date()): uint32` — `YYYY-MM-DD` (UTC) 추출 → `hashStringSeed`
2. `dungeon-generator.js` 의 mulberry32 정의를 `import { mulberry32 } from './rng.js'` 로 교체 (중복 제거)
3. **AI 알고리즘 측 Math.random 은 절대 건드리지 않음** — B-108 비고와 동일 원칙. 시드는 *세계 생성* 에만 적용, *학습 stochasticity* 와 분리

**검증**:
- 같은 seed → 같은 dungeon 출력. `node -e "import('./web/js/game/rng.js').then(m => { const r = m.mulberry32(42); console.log([r(),r(),r()]); })"` 두 번 → 동일
- `dailySeed(new Date('2026-05-12'))` 결과를 다른 timezone 에서 호출해도 동일 (UTC 기준)

#### T2B-1.2 — Daily Seed 모드 + 데일리 던전 (~2일)

**작업**:
1. Daily Seed 모드 진입점 — Play / Editor 탭 옆에 **Daily** 탭 추가 (`<button class="mode-tab" data-mode="daily">`). 한국어 라벨 "오늘의 도전".
2. Daily 모드는 일반 캠페인 런과 별개 — `runState` 의 일부지만 isolated:
   - `runState.dailyAttempts: { [dateKey]: { seed, cleared, bestSteps, deaths, modifierIds } }`
   - 진입 시 `currentDateKey = utcDateKey(new Date())` 계산
   - 같은 날짜는 1회만 (또는 무제한 재시도 + 첫 성공 기록만 카운트). MVP 는 **무제한 재시도, 첫 성공 기록 보존**
3. Daily 던전 = `generateDungeon(width=20, height=20, { seed: dailySeed() })` (PCG 변주). 캠페인 던전과 별개. 한 화면 안에 들어가는 중간 크기.
4. UI:
   - 데일리 모드 진입 화면: "오늘의 시드: 2026-05-12 #(seed)" + 적용된 모디파이어 (T2B-2 후) + "도전" 버튼
   - 클리어 후: "어제 +3 스텝" / "오늘 첫 성공!" 같은 자기 비교 메시지

**산출물**:
- `web/js/game/daily-mode.js` 신규 모듈 — daily run state + 진입/이탈 로직
- `web/js/main.js` 의 mode-tabs 핸들러 확장
- `web/index.html` Daily 탭 + 진입 화면 마크업
- `web/css/style.css` 진입 화면 스타일

**검증**:
- 같은 날 reload 후에도 같은 시드/같은 던전 layout
- 시간대 바뀐 가상 시계 (e.g. `agent-browser eval` 로 Date 모킹) 으로도 동일 날짜에서 같은 시드
- 새 날짜로 가면 새 시드/새 던전

## 3. 다음 작업 명세 — T2B-2 모디파이어 3종 MVP (~2~3주)

### 3.1 목적
"매 런 다른 모디파이어로 같은 던전도 다르게 풀린다" — D-4 verdict. 자기 정체성 문장의 핵심 부분 ("매 런 다른 모디파이어").

### 3.2 3종 MVP (BACKLOG)

| 모디파이어 | 효과 | 구현 비용 |
|---|---|---|
| **미끄러운 바닥** (slippery) | 이동 방향이 30% 확률로 옆으로 빗나감 | **저** — 기존 `slippery: true` flag 이미 일부 던전에 적용됨 (Lv.26~28). 던전 config 가 아닌 *런타임 modifier* 로 격상하면 됨 |
| **두 명만** (two-only) | 한 런에서 사용 가능한 세르파를 2명으로 제한 (선택지 좁힘) | **중** — 캐릭터 선택 UI 에서 락 + run-state 의 hiredCharacters 제한 |
| **안개 짙음** (heavy-fog) | fog of war 의 가시 범위를 절반으로 축소 (현재 N → N/2 칸) | **저** — agent.js 의 `getVisibility` 보정 |

### 3.3 작업 분해

#### T2B-2.1 — ModifierManager 모듈 (~2일)

`web/js/game/modifiers.js`:
```js
export const MODIFIERS = {
  slippery:    { id: 'slippery',    name: '미끄러운 바닥',     desc: '이동이 30% 확률로 옆으로 빗나갑니다.' },
  two_only:    { id: 'two_only',    name: '두 명만',          desc: '한 런에 세르파 2명만 사용 가능.' },
  heavy_fog:   { id: 'heavy_fog',   name: '안개 짙음',         desc: '시야 범위가 절반으로 축소됩니다.' },
};

export class ModifierSet {
  constructor(ids = []) { this.ids = new Set(ids); }
  has(id) { return this.ids.has(id); }
  // hook 메서드들 — 각 작용 지점에서 호출
  applyMovement(intendedAction, rng) { /* slippery */ }
  applyVisibility(baseRange) { /* heavy_fog */ }
  filterCharacterPool(allChars) { /* two_only — pool 2 명 픽 */ }
}

export function pickModifiers(seed, count = 1) { /* PRNG 으로 후보 중 N 개 추출 */ }
```

#### T2B-2.2 — 각 모디파이어 효과 통합 (~3일)

- **slippery**: `web/js/main.js` handleAction + sim simulator manualPlayResult 의 stochasticity 분기. PRNG 는 *모디파이어가 활성화된 동안의 별도 RNG* — 사용자 입력에 의존하지 않는 결정론
- **two_only**: 데일리 모드 진입 시 캐릭터 2명 자동 픽 (시드 결정) — 데일리 던전 + two_only 모디파이어가 같이 적용되는 경우
- **heavy_fog**: `web/js/game/agent.js` 의 `getVisibility` 가 ModifierSet 을 의식하도록. 또는 main.js 에서 `agent.visibilityRangeOverride = 2` 같은 인자 주입

## 8. 알려진 위험 / 함정

### 8.1 agent-browser module cache
- ES module 변경 시 reload 만으로는 새 코드 안 로드. close→open 필수
- (재발 시) cache buster ?v=$(date +%s) 도 효과 있음

### 8.2 localStorage 잔여 데이터
- Step-0 진입 검증 (B-004) 시 이전 클리어 기록 남아있으면 무용. 검증 전 `localStorage.clear()` 필수

### 8.3 baseline noise
- 5-run 결과는 ±5 던전 변동 가능. 20-run 으로 안정화 (1분 미만 소요)

### 8.4 grid.js 던전 데이터 보존
- Lv.20~23 grid 데이터는 *unused but preserved*. 검색해서 "안 쓰이니까 지우자" 가지 말 것. NG+ 재활용 후보

### 8.5 AI 측 비용 상수 (절대 수정 금지)
- `BASE_OP_COST` / `MAX_EPISODES` / `CONVERGENCE_THRESHOLD` 는 D-4 verdict 의 핵심 제약
- 발란스 조정 시 *수동 측 비용* (B-108 의 MANUAL_FOOD_PER_STEP) 만 건드림
- 위반 시 D-4 가 반복한 디베이트 다시 발생 — 옹호 A의 "이코노미 수술" 노선 부활 위험

### 8.6 정체성 카피 통일 (B-001)
- README / GDD / ACT1_SUMMARY / VISION 의 정체성 문장은 §0 의 D-4 문장. 인게임 새 카피 작성 시 이 문장과 *공존 불가* — 새 카피가 D-4 와 모순되면 디베이트 재개
- 가차 (NPC 가챠) / 던전 마스터 모드 메인 등은 D-5 / D-4 로 *영구 컷* — 다시 메인 카피로 들이지 말 것
